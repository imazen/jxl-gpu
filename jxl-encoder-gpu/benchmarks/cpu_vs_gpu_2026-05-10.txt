======================================

Hardware: AMD Ryzen 9 7950X + RTX (CUDA backend, cubecl 0.10)
Method:   5 runs each after warmup, distance/effort/iters as labeled.
GPU path: prepare_strategy_search_plan + N × encode_with_strategy_plan_adaptive
          (lossy pipeline, NO bitstream output yet)
CPU path: jxl_encoder::api::LossyConfig encode (full pipeline → JXL bytes)

Observations
------------

1. **GPU scales much better with image size.**
   1024² has 4× the pixels of 512² but GPU only takes ~2× as long
   (67 vs 31 ms). CPU takes ~5-6× as long (426 vs 76 ms). The GPU
   has higher fixed setup cost but its parallel work amortizes.

2. **CPU is slower at higher distance.**
   d=4 takes longer than d=1 on the same image. Counterintuitive
   for a "lossier" setting; likely because the strat-search picks
   more large-transform candidates that need bigger cost-grid evals,
   and the entropy codec spends more effort optimizing the cleaner
   coefficient distributions.

3. **GPU is invariant to distance.**
   d=1 and d=4 take essentially the same GPU wall-clock (67 vs 68 ms
   at 1024²; 31 vs 29 ms at 512²). The cost-grid evaluation runs all
   strategies regardless; selection just changes which one is picked.

4. **Speedup grows monotonically with pixel count.**

   | Pixels   | Speedup at d=1 | Speedup at d=4 |
   |----------|----------------|----------------|
   | 0.26 MP  |  2.5×          |  4.7×          |
   | 1.05 MP  |  6.4×          |  8.9×          |
   | 2.78 MP  | 10.7×          | 15.9×          |

   At 0.26 MP the GPU's fixed setup overhead (~30 ms) dominates;
   the parallel work is small. By 2.78 MP the parallel work has
   amortized that overhead 3-4× over and the speedup is huge. A
   ~true 4K image (8.3 MP, 3× the 2048×1360) would likely sustain
   or exceed the 10-16× range — the GPU number plateaus near the
   ~100 ms / image floor while CPU keeps scaling linearly.

5. **GPU encode time barely depends on pixel count above 1 MP.**
   1024² and 2048×1360 took 67 ms vs 104 ms for 2.65× more pixels.
   The ~37 ms extra is mostly cost-grid + IDCT + scatter scaling
   linearly with pixel count, but the prepare overhead (XYB,
   gaborish, mask1x1) stays roughly fixed. Indicates the GPU is
   under-utilized at smaller sizes — fixed-cost stages dominate.

6. **At 16-20 MP, CPU scales linearly while GPU stays sub-linear.**
   16 MP: 5.99 s CPU, 0.67 s GPU = 8.9× (CPU = 0.37 s/MP)
   20 MP: 7.63 s CPU, 0.85 s GPU = 9.0× (CPU = 0.38 s/MP)
   Speedup peaked at 2.78 MP native (10.7×) and held ~9× through
   the larger Lanczos3-upscaled sizes. The Lanczos3 upscale
   smooths high-frequency detail, biasing AC strategy mix toward
   larger transforms — which CPU handles relatively faster than a
   native 16+ MP photo would. Speedup on a true native 16+ MP
   photo would likely be higher.

7. **>20 MP cliff.** 32 MP and 48 MP both hung beyond a 10-min
   timeout even with Triangle (bilinear) upscale (which is fast).
   Triangle resize at 32 MP completes in seconds, so the hang is
   downstream — either the CPU encoder OOMs / spends huge time on
   AC strategy search at large sizes, or the GPU memory pool
   blows up with ~10 plane-sized intermediates at 1+ GB total.
   To localize: split the bench into CPU-only and GPU-only modes,
   try each in isolation. Not investigated this session.

   For now: 16-20 MP is the upper measured limit on this bench.
   Speedup at that size is ~9× (CPU 0.37 s/MP linear; GPU 0.04
   s/MP including amortized fixed cost).

Caveats
-------

- GPU number is the lossy pipeline only. Bitstream output (entropy
  coding + frame headers + container) is still CPU-only and would
  add an estimated ~50-150 ms depending on strategy mix and
  histogram complexity. Even adding that, GPU-lossy + CPU-bitstream
  beats CPU-full by ~3-4× on 1024².

- Both warmed up: cubecl pool is hot, jxl-encoder caches are
  primed. First-run numbers are higher (cubecl JIT compile of
  kernels can take ~1 s on cold start).

- GPU bitstream port is the next big lever for end-to-end speedup.
